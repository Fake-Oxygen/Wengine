# Implementation Plan: Comprehensive Code Documentation

**Branch**: `009-comprehensive-code-documentation` | **Date**: 2026-11-19 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/009-comprehensive-code-documentation/spec.md`, plus planning-phase user input: "Documentation should be generated using sphinx, myst and doxygen. So especially comments in code must follow doxygen conventions to be rendered properly. I want html version of the full documentation and it should be indexed in logical manner, so that i'm not required to hunt for the actual docs that im interested in."

## Summary

The engine's knowledge currently lives in a repository-literate README, seven
topic guides, and the original authors' heads. This plan delivers the spec's
documentation suite as a single, logically indexed HTML site generated by
the user-mandated toolchain: **Sphinx 9 + MyST-Parser** render the authored
pages (developer guide, end-user guide, test/benchmark/example catalogs) as
Markdown; **Doxygen 1.9.8** extracts the public API (129 headers, 12 module
directories under `include/wengine/`) from **Doxygen-convention comments**;
**Breathe 5.1.0** bridges that XML into curated per-module API pages; **furo**
supplies audience-oriented sidebar navigation plus full-text search so no
reader hunts for a topic. A comment-only source pass brings every public
definition to contract level in Doxygen syntax (verified bit-identical
build/test outcomes), audit tooling proves catalog completeness against the
74 registered tests / 12 benchmarks / examples inventories and proves API
coverage via Doxygen's own undocumented warnings, and a documented
regeneration process keeps the site from rotting after code changes.

## Technical Context

**Language/Version**: C++20 codebase (documented, not behaviorally changed).
Docs toolchain: Sphinx 9.1.1 + MyST-Parser 5.1.0 (host-installed), Breathe
5.1.0 and furo 2025.12.19 (pinned in `docs/requirements.txt`, pip-install),
Doxygen 1.9.8 (host; Breathe requires ≥ 1.9.2 — satisfied).

**Primary Dependencies**: `sphinx`, `myst-parser`, `breathe`, `furo`,
`sphinx-copybutton` (already installed). All Python deps live only in the
docs build; engine builds gain zero new dependencies.

**Storage**: In-repo MyST sources under `docs/` (new subdirectories;
existing topic guides stay in place, included by the toctree — never
forked, per FR-009). Generated HTML and Doxygen XML are out-of-tree at
`build/docs/{html,doxygen-xml}/` (inside the already-ignored build dir,
preserving the out-of-source discipline).

**Testing**: Four verification layers, no engine test targets added:
(1) catalog audits — a small Python script compares inventories (ctest
registration, benchmark/example files) against catalog entries;
(2) API coverage audit — Doxygen runs with `EXTRACT_ALL=YES` +
`WARN_IF_UNDOCUMENTED`, undocumented public entities surface as warnings
that must reach zero; (3) documentation accuracy pass — every documented
command/example is executed as written (FR-013/SC-006); (4) comment-only
safety — the full `ctest` suite runs before and after the in-code pass with
identical results (SC-007). GUI walkthrough pages are verified by manual
windowed runs per project practice.

**Target Platform**: Linux for building (project baseline); the output is
static HTML viewable in any browser.

**Project Type**: Documentation suite over the existing header-only
engine + CLI/TUI/GUI front ends. No new engine targets, commands, flags,
registries, or file formats.

**Performance Goals**: N/A — no runtime code changes. Docs build is
on-demand, not a gate for engine builds.

**Constraints**: Comment-only edits to C++ (zero behavior change, SC-007);
Doxygen-convention comments are mandatory for rendering (user requirement);
existing docs corpus is cross-referenced, never duplicated or contradicted
(FR-009/FR-010); README remains the living spec it already is (new pages
link into it, no rewrite); the `assert()`-macro comma pitfall (AGENTS §11)
applies while editing near test code — comments must never reflow code.

**Scale/Scope**: 12 engine module directories (129 public headers) in the
API reference; 74 registered tests plus test-support scripts in the test
catalog; 12 benchmarks; ~12 examples (C++, Python, Zephyr); three front ends
(CLI+REPL, TUI, GUI); 7 existing topic guides + README + GLOSSARY folded
into the navigation. Source edits are comment-only and spread wide by
design; behavior surface is zero.

**Structure Decision**: `docs/` is the Sphinx source root because the
existing topic guides already live there — they join the toctree from
their current locations (AGENTS.md/README link stability preserved), and
MyST is a CommonMark superset so they render unmodified. Root-level
README.md and GLOSSARY.md remain repository documents linked from the
landing page rather than copied into the site (no content forking;
trade-off: they are outside Sphinx search — recorded in
`research.md` R3). The API reference is hand-curated per module rather
than a generated exhale-style dump; each module page pairs prose and a
usage pattern with breathe directives plus an auto-generated entity index
for that module, so navigation stays logical while coverage stays
auditable (R1).
